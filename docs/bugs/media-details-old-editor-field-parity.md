# Media details field parity with the old editor's edit panel (Link, Target, Alt, Width, Radius, Align, License)

**Status:** Fixed
**Area:** core (`atom/schema.ts`, `atom/formats.ts`, `list/formats.ts`, `modelDom.ts`, `surface/renderer.ts`) + react (`MediaDetailsPopover.tsx`, `CanonicalAuthorityEditor.tsx`)
**First reported:** 2026-08-31/09-01, "Codex prompt — media details editing: match old editor's field set, investigate before building" - a screenshot of the old Sootr editor's right-click media panel (Link, Target, Alt, Width, Radius, Align, plus a License section: description/source URL/type/version/attribution and Replace/Reset/Delete/Close) as a reference field set, with an explicit standing instruction to investigate existing capability before building anything new.
**Related files:** `docs/bugs/table-cell-border-color-width-no-ui.md` (the "written, never rendered" pattern this investigation was told to check for specifically), `packages/react/src/components/TableBorderPopover.tsx` (the compact multi-field popover pattern this reuses), `packages/react/src/components/MediaOverlay.tsx` (unmodified - the trigger surface), `packages/react/src/mediaProvider.ts` (`MediaItem.license`'s existing shape)

## Investigation - field-by-field disposition, per the standing instruction to check before building

- **Alt** - already fully wired (schema, renderer, UI via the old `window.prompt`). Replaced the prompt with a real form field in the new panel; no model-level change needed.
- **Align** — **UI-only gap**, exactly the project's recurring "written, never rendered" pattern (matches `table-cell-border-color-width-no-ui.md`'s own precedent). `atom/schema.ts`'s `imageAttrs.align` already existed with full validation, and `surface/renderer.ts` already applied real `display`/`float`/`margin` CSS for `center`/`left`/`right` — there was simply no UI control to set it. Added to the new panel with zero schema/command work.
- **Width** — already fully wired (schema, renderer, existing drag-handle/±20 UI). The panel's own Width field reuses the existing `resizeAtom` command via `updateAtom`, preserving aspect ratio the same way the drag handle already does — no new "Height" field, matching the old editor's own screenshot (it had no separate height input either).
- **Link (href) / Target** — **genuinely missing at every layer** (schema, commands, renderer, formats, UI) — confirmed via direct grep of `atom/schema.ts`'s `imageAttrs` and every image-handling branch in `surface/renderer.ts`/`atom/formats.ts`/`modelDom.ts`/`list/formats.ts`: no href-like attribute existed anywhere on any atom type. Full stack built (see Design below). The `link` *mark* already has this exact shape, but marks are explicitly disallowed on every atom (`marks: ""` in `atom/schema.ts`) — a dedicated pair of atom-level attrs was the only option, not a reuse of the mark.
- **Radius (corner rounding)** — **genuinely missing**, confirmed absent via the same grep — no `borderRadius`/similar attribute existed on any atom. Added as a new numeric attribute (px), rendered as real `border-radius` CSS, following the same shape as the recently-added table cell border-width work the prompt pointed to as precedent.
- **License (description, source URL, type, version, attribution)** — **genuinely missing at the schema level**, but the *data* was already reachable and already being discarded: `MediaManager.tsx`'s own info panel (lines ~404-407) already displays `item.license.{workName,author,licenseType,licenseText,sourceUrl}` for library-sourced images, and `MediaItem.license` (`mediaProvider.ts`) already has this exact shape — but `CanonicalAuthorityEditor.tsx`'s `selectFromMediaManager` (the function that actually inserts a picked library item) never read `item.license` at all, so this real, already-fetched data was silently thrown away at exactly the insertion boundary. Added `licenseDescription`/`licenseSourceUrl`/`licenseType`/`licenseVersion`/`licenseAttribution` atom attrs and wired `selectFromMediaManager` to copy `item.license` across. `licenseVersion` has no `MediaItem.license` equivalent (that shape has no separate version field) — always user-entered via the panel, same as for a freshly uploaded image with no provider metadata at all.
- **Replace/Reset buttons** (from the old screenshot) — **not applicable to this architecture**, not a gap. "Replace" would mean swapping the underlying image file/URL while keeping the atom's other attrs - the current insertion flow (`MediaManager`/`DefaultMediaPicker`) has no equivalent "replace this specific atom's source" entry point at all, and building one was outside this prompt's field-parity scope (it names Link/Target/Alt/Width/Radius/Align/License explicitly, not a re-upload flow). "Reset" (revert to original values) is subsumed by the panel's own Cancel/Escape, which already discards any unapplied changes.

## Design decisions confirmed explicitly, not silently

- **Panel location: stays part of `MediaOverlay`'s selection-triggered flow, not a reintroduced context-menu entry.** The Direction B redesign's context-menu scope reduction (table-only, media moved to a dedicated overlay) is a deliberate, already-documented architecture decision (`context-menu-scope-reduction.md`) — confirmed consistent with it rather than reversed: `editSelectedAtom()` (the existing `MediaOverlay` "Edit" button handler) now opens the new panel instead of a `window.prompt`, with zero changes to how the overlay itself is triggered.
- **License fields: independently user-editable, auto-populated from `MediaProvider` only when real data exists.** Checked how images actually get inserted before assuming either "always blank" or "always from the provider": a freshly uploaded image (`DefaultMediaPicker`, or a genuinely new `MediaManager` upload) has no license metadata at all — `MediaProvider.upload()`'s own return type is only `{url, id}`, correctly reflecting that a brand-new upload has nothing to auto-populate. A library-sourced image picked via `MediaManager`'s search/duplicate-detection paths, by contrast, already carries a real `MediaItem.license` from the provider — auto-populated at insert time (`selectFromMediaManager`), then freely editable afterward via the panel, matching how a real host's asset library would supply license data for a known asset while still letting a user correct or fill in gaps.
- **Live DOM encoding for href/target/radius/license: plain `data-smart-*` attributes on the existing `<img>`/`<div>` element, not a wrapping `<a>`.** `surface/renderer.ts`'s diffing contract depends on stable per-node element identity across re-renders; introducing a conditional DOM-structure change (wrap/unwrap an `<a>` based on whether `href` is set) for something `surface/input.ts`'s click handling can read directly as an attribute was unnecessary structural risk. Ctrl/Cmd+click opens the link via the exact same mechanism the existing text-link mark already uses (`CanonicalAuthorityEditor.tsx`'s `onMouseDown`/`onClick` handlers, extended to also check `closest("[data-smart-href]")` alongside the existing `closest("a[href]")`).
- **String-export encoding (`atomToHtml`/`modelDom.ts`): a real `<a>` wrapper.** Both are one-shot tree builders (clipboard/print DOM, exported HTML string) with no per-node element identity to preserve — and a link needs a genuine anchor to survive and function outside this live editor at all (in a pasted-elsewhere document, a raw HTML consumer, a printed page). `atomFromHtmlElement` (the isolated fidelity-test parser, `atom/formats.ts`) unwraps this exact `<a><img></a>` shape back to the atom's own attributes as its own round-trip inverse.
- **Third-party `<a><img></a>` paste behavior: block-level unwrap-and-drop kept exactly as-is.** `list/formats.ts` already had a deliberate, evidence-based decision (a real captured Wikipedia "copy image" clipboard payload) to drop an incidental link wrapper around a block-level pasted image, since that link is almost always the source page, not something a user authored via this feature. Explicitly did **not** extend that block-level path to also read `href` from a third-party `<a>` — only from this app's own `data-smart-href` marker — so this new capability couldn't silently reverse an already-correct prior decision. The **inline** `image` atom's parsing (a different code path, used for an image sitting inside running text) does still recognize a link from an inherited `link` mark's ancestor `<a>`, since an inline image acting as part of a hyperlinked run (an icon/badge pattern) is a normal, intentional real-world case, confirmed via a dedicated regression test.

## A pre-existing bug found and fixed while verifying "clear align back to None"

`surface/renderer.ts`'s image-align branch had `if (center) {...} else if (left/right) {...}` with no final `else` — setting align to `center`/`left`/`right` correctly applied `display`/`float`/`margin`, but there was no code path to ever *remove* those styles again once align became unset, because "align was set, then explicitly cleared" was never a reachable transition before this UI gave a user any way to do it. Found via the new panel's own "None" align option failing its own regression test (`float` stayed `"left"` after switching to "None"). Fixed by adding the missing `else` branch, removing `display`/`float`/`margin` explicitly - the same set/remove pairing every other conditional style branch in this same function (e.g. `borderRadius`, right below) already uses correctly.
