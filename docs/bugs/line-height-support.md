# Line height support

**Status:** Implemented
**Area:** core (`block/schema.ts`, `block/commands.ts` reused as-is, `surface/renderer.ts`, `list/formats.ts`, `formats/docx/export.ts`, `block/formats.ts`, `formats/fidelity.ts`), react (`toolbarTools.ts`, `components/CanonicalAuthorityEditor.tsx`, `components/ToolbarPrimitives.tsx`)
**First reported:** "Codex prompt — line height support" (2026-09-07), explicitly standalone from the same day's horizontal-line/page-break work.
**Related files:** [horizontal-line-and-page-break-tools](horizontal-line-and-page-break-tools.md) (the same day's other new-capability feature, same verification discipline applied here).

## Design decisions locked

- **Granularity: per-paragraph/block attribute**, matching `align`/`indentLevel` exactly - added to the same shared `blockAttrs` object in `block/schema.ts`, so it's automatically available on every block type that already carries alignment: `paragraph`, `heading`, `blockquote`, `code_block`. Table cells need no schema change of their own: a cell's content is itself paragraphs, which already support the attribute directly - confirmed this is exactly how alignment already reaches table-cell content today (no `table_cell`-specific attribute exists for `align` either).
- **Value representation: a unitless multiplier** (`1`, `1.5`, `2`, ...), matching CSS `line-height`'s own unitless mode - deliberately not a fixed px/pt value, which would stop scaling correctly the moment `fontSize` changes on the same block. Validated in `block/schema.ts`'s `lineHeightAttr` as a finite number in `[0.1, 10]` - generous but bounded (Google Docs' own preset list tops out at 2.5).
- **Presets + custom entry**: five presets (1, 1.15, 1.5, 2, 2.5, matching Google Docs' own reference list) as toolbar menu items, plus a "Default" entry (clears the override) and a labeled numeric `<input>` for an arbitrary custom value - the same "menu items plus an embedded native form control" shape already established by the List preset dropdown's own `<select>` (`CanonicalAuthorityEditor.tsx`'s `listPresetSelect`), not a new UI pattern.
- **Default value**: absence of the attribute (not a forced `"1"`) means "no override" - the block renders at the browser/font's own natural line-height. The renderer only ever sets `element.style.lineHeight` when `node.attrs?.lineHeight` is present, and removes the inline style otherwise (mirrors `align`/`indentLevel`'s identical pattern in `surface/renderer.ts`'s `syncNodeAttributes`). "Default" in the toolbar explicitly calls `setLineHeight(undefined)`, which `setBlockAttributes`'s existing `cleanAttrs` step already strips from the node's `attrs` entirely - clearing to default was free, no new command logic needed.

## A real design risk found and corrected before shipping

Initial implementation had `parsedBlockAttrs` (HTML import) fall back to a bare CSS `line-height` value when no `data-smart-line-height` marker was present - mirroring exactly how `align`/`indentLevel` already fall back to their own bare CSS equivalents. This looked right by analogy but was wrong: re-running the full clipboard corpus test suite (a standing regression gate) showed two real captured fixtures - `google-docs-clipboard.clipboard.json` and, notably, `native-smart-rte-clipboard.clipboard.json` (a real copy from this editor's own output) - carry an explicit `line-height` CSS declaration on **every single paragraph**, at values (`1.3800000000000001`, `1.6`) that are document-wide/ambient defaults, not per-paragraph overrides. For the native fixture specifically, `1.6` is literally this editor's own global `line-height: 1.6` (`theme.ts`'s `.srte-canonical-authority > .srte-editor[contenteditable]` rule) baked onto every element by the browser's own clipboard serialization, not a value the user ever deliberately applied to that paragraph.

`text-align`/`margin-inline-start` do not have this problem in practice - browsers do not routinely bake an ambient default onto every paragraph's inline style the way they clearly do for `line-height`. Recognizing the bare CSS value would have silently attached a meaningless "explicit" `lineHeight` attribute to every paragraph in any pasted Word/Google Docs/self-copied document. **Fixed by removing the CSS-value fallback entirely** - only this app's own explicit `data-smart-line-height` marker (written exclusively when the user deliberately applies a value via the toolbar) is trusted on import. Re-ran the corpus suite after the fix: both fixtures' locked structural hashes returned to their pre-change baseline, confirming the fallback was the only difference and that the fix restores the correct behavior.

## Format round-trip fidelity (new `"line-height"` row in `formats/fidelity.ts`)

| Format | Level | Why |
|---|---|---|
| HTML | **full** | `data-smart-line-height` attribute plus an inline `line-height:` style declaration round-trips exactly (`list/formats.ts`'s `blockAttributes`/`parsedBlockAttrs`). |
| PDF | **full** | This package's actual "Save as PDF" is a real browser print of the same HTML export (`formats/pdf/format.ts`'s `buildPdfPrintDocument` → `serializeCanonicalListHtml`), so it inherits the HTML row's real, correctly-spaced layout exactly - **verified against the real print popup's own computed styles** (e2e test, see below), not assumed from the HTML string. |
| DOCX | **lossy** | Real Word "multiple" line spacing (`<w:spacing w:line="..." w:lineRule="auto">`, `formats/docx/export.ts`'s `paragraphProperties`) is emitted on export - Word itself displays the correct spacing when the file is opened. Confirmed **empirically** (not assumed) that mammoth's HTML conversion (this package's own DOCX import path) drops the spacing value entirely on re-import - the same asymmetry already documented for `page-break`. |
| Markdown | **unsupported** | Markdown has no line-spacing concept at all. The paragraph's own text is preserved in full - only the spacing metadata is dropped, not the content - matching this project's non-destructive-fallback discipline. |

`block/formats.ts`'s `blockToDocxEntry`/`CanonicalDocxBlock` (the per-node projection `featureCodecs.ts`'s fidelity-table tests exercise) also gained a `lineSpacing240ths` field, wired the same way `headings-alignment`/`blockquote-code` already are - real DOCX-only codec wiring, no fabricated HTML/Markdown/PDF per-node wrapper (matching the project's own "wire what already exists" rule; HTML/Markdown/PDF for this feature remain whole-document-walker concerns, verified via `serializeCanonicalListHtml`/`serializeCanonicalListMarkdown`/`buildPdfPrintDocument`'s own tests directly, same as every other block-level feature).

## Implementation

- **Schema**: `lineHeightAttr` added to `blockAttrs` (`block/schema.ts`), applying to paragraph/heading/blockquote/code_block.
- **Command**: none needed - `setBlockAttributes` (already generic, already used by every align button) is called directly with `{ attrs: { lineHeight: value } }`, exactly the same call shape the four alignment buttons already use.
- **Renderer**: `surface/renderer.ts`'s `syncNodeAttributes` sets/clears `element.style.lineHeight` from `node.attrs?.lineHeight`.
- **Toolbar UI**: new "Line spacing" `ToolbarDropdown` in the Paragraph group (next to the four align buttons, before "More paragraph tools") - chosen over the Format/text-styles group since line spacing is a paragraph-level property like alignment/indent, not an inline text-formatting one. Five preset `ToolbarMenuItem`s, a "Default" item, and a labeled custom-value `<input type="number">`, duplicated verbatim into `MobileMoreMenu` (the same desktop/mobile parity-by-construction pattern every other toolbar tool in this file uses). A real bug caught mid-build: an initial `id="srte-line-height-custom"`/`<label htmlFor>` pairing collided the moment both the desktop and mobile copies were mounted simultaneously (always true - CSS visibility, not conditional rendering, is what hides one of them) - fixed by switching to `aria-label` (no uniqueness constraint), matching how the List preset `<select>` already avoids this exact problem.
- **Active-state/mixed-selection display**: `SelectionDescription` (the existing mark-coverage mechanism `markCoverage` uses) has no equivalent for block *attributes* - only `blockTypes: string[]` (node types, not attrs). Built a new `selectedLineHeightBlockIds`/`currentLineHeight` pair in `CanonicalAuthorityEditor.tsx`, mirroring `block/commands.ts`'s own (core-internal, not exported) `blockScopes`/`selectedBlockIds` traversal - resolves every block ID in the current block-range/mixed scope and reads each one's `attrs.lineHeight` directly, returning a value, `undefined` (no selection or no override anywhere), or `"mixed"` (selected blocks disagree) - the same three-state shape as `markCoverage`'s `boolean | "mixed" | undefined`. A mixed selection needs no special-casing to suppress checkmarks: every `pressed={currentLineHeight() === preset}` comparison naturally evaluates `false` against the `"mixed"` sentinel.
- **`tools` prop**: new `tools.lineHeight` key, defaulting to visible, automatically covered by the existing exhaustive `DEFAULT_TOOLBAR_TOOLS` completeness test.

## A test regression found and fixed during verification

The full e2e suite run for this feature surfaced two WebKit-only failures that were **not** feature bugs: `canonical-toolbar-routing.spec.ts`'s "routes lists, links, tables, atoms, resize, import, and export through retained state" and `media-details.spec.ts`'s "sets link, radius, and align...". Both were bisected (by reverting each changed file individually and re-running in isolation) to a pre-existing race in those two tests - an immediate click/visibility assertion on a freshly-inserted image, unmocked, racing a live (always-failing) DNS lookup whose timing WebKit's own broken-image rendering is sensitive to. This feature's own change (trivial extra field reads inside `blockAttributes`/`parsedBlockAttrs`, run on every transaction via the playground's `onHtmlChange` wiring) was enough added wall-clock cost to consistently tip that pre-existing race over. Fixed by mocking the image response in just those two tests, matching the pattern already established in `canonical-authority.spec.ts`. Full writeup: [webkit-broken-image-zero-size-race](webkit-broken-image-zero-size-race.md).
