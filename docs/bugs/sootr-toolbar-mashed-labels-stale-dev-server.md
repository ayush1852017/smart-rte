## Correction (2026-08-31, same day)

The dev-server restart below was performed and genuinely necessary (Sootr's `next dev` really had been running since Aug 21, 10 days stale) - but it did **not** fix the reported symptom. The user reloaded after the restart and sent follow-up screenshots showing the identical mashed-label pattern, this time unambiguously against the *new* editor (the screenshots show "Version history", "Insert formula", "Special characters" - all new-canonical-editor-only labels, proving the new code was actually running). That falsified the "stale dev server" conclusion below. Two further symptoms were also reported in that follow-up that this investigation never considered: the toolbar was unresponsive to clicks, and the editor's height was fixed with no internal scroll.

Re-investigating with that new evidence found the real cause in minutes: `theme.ts`'s wide-viewport-promotion breakpoint (`toolbar-priority-collapse-fixed-threshold-no-wide-promotion.md`) paired a `@container srte-editor (min-width: 1440px)` rule with a plain `@media (min-width: 1440px)` fallback. The `@media` form checks the *browser window* width, not the editor's own rendered width - in a split pane the window can be wide (≥1440px) while the editor's own container is narrow, and the `@media` rule fired anyway, promoting 9 extra buttons into a group with no room for them. This one CSS defect explains both the mashed labels (content squeezed below its natural size) and, very likely, the "unresponsive toolbar" (overlapping button hit-boxes misdirecting clicks) - confirmed directly by testing clicks at the exact repro width. See the real writeup for the full mechanism, fix, and verification.

The "editor height fixed, no scroll" symptom was unrelated: a separate, independently-dead CSS selector in Sootr's own `globals.css` (also documented below and fixed in the real writeup).

**Lesson for next time**: a plausible, evidence-backed theory (stale process predating the fix, confirmed via `ps -o lstart`) is not the same as a *confirmed* one - the standing rule to verify via real interaction, not just a synthetic sweep, applies to confirming a "not a bug" conclusion just as much as a "this is the bug" one. The synthetic playground sweep that supposedly ruled out a package defect never actually tested the one variable that mattered (a container narrower than the window), because a single top-level playground page can't produce that divergence via `page.setViewportSize` alone - this should have been a signal to build a wrapped/constrained-container repro *before* concluding "not a bug," not after the theory was already falsified by the user.

## Investigation

Per `CLAUDE.md`'s standing rule, checked `docs/bugs/` first and read `toolbar-priority-collapse-fixed-threshold-no-wide-promotion.md` in full before starting, since the report explicitly suspected a gap in that fix's tested width range (640–1439px, only verified at 800px/1280px, never continuously swept).

**Attempted reproduction in the package's own environment, exhaustively, before touching any code:**
- Swept the standalone playground's toolbar (full feature set — table/media/formula all enabled, matching Sootr's real "study-material" configuration) across **every 30–60px increment from 340px to 2300px**, in **all three Playwright engines** (chromium, firefox, webkit), checking both (a) any two same-row `.srte-tool-button` elements overlapping, and (b) any button's `scrollWidth` exceeding its rendered `getBoundingClientRect().width` (the signature of content being squeezed below its natural size). **Zero overlaps and zero meaningful shrink found anywhere in this range**, in any engine (one trivial 6px case in Firefox at an extreme 340px, unrelated to the ~700-800px width in the report).
- Took real screenshots at 650/700/750/900px — all render cleanly, correct wrapping, no mashing.
- Read Sootr's real split-pane layout source (`app/[...]/blocks/[blockId]/page.tsx`): the editor panel uses `style={{ width: `${splitPercent}%`, minWidth: showPreview ? '25%' : undefined }}` — a percentage-based min-width floor rather than a fixed pixel floor, a real (if separate) hardening gap worth flagging to Sootr's maintainers, but mechanically produces the same *final resolved pixel width* for the editor's container as a direct viewport resize, which the sweep above already covers exhaustively.
- Read Sootr's own `app/globals.css`: it contains four `.smartrte-container > div:first-child > div:first-child`-style rules explicitly commented "Allow the toolbar to wrap on smaller screens" — clearly written against an **older editor version**, since these selectors only match when `.smartrte-container`'s first child is literally a `<div>`. The current canonical editor's root is `<section class="srte-root srte-editor srte-canonical-authority">` (`CanonicalAuthorityEditor.tsx:1620`) — a `<section>`, not a `<div>` — so `div:first-child` cannot match it at all. **Confirmed empirically**: replicated Sootr's exact wrapper (`<div class="smartrte-container">` around the real rendered editor root) and Sootr's exact override CSS in a live Playwright page; `document.querySelector('.smartrte-container > div:first-child')` returned `null`. These rules are dead code against the current DOM.
- The fact that these overrides were written to match a plain-`<div>`-rooted editor, combined with checking how long Sootr's actual `next dev` process (PID 28245) had been running: **`ps -o lstart` showed it started Fri Aug 21 15:29:23 2026** — 10 days before this session bumped `smartrte-react`/`smartrte-core` from `0.3.4` to the newly-published `1.0.0-beta.1` and ran `npm install` in Sootr's repo (same session, immediately prior to this report). Next.js's dev server does not pick up a `node_modules` version change in an already-running process — this exactly matches the standing pattern in `stale-dist-build-confusion.md` ("check `ps -o lstart` for how long the dev server process has actually been running, and restart it if it predates the fix, even if the alias config itself is correct").

**Conclusion: the screenshot was taken against Sootr's long-running dev server still serving the old, pre-upgrade `0.3.4` DOM-authoritative editor** (whose plain-`<div>` root is exactly what Sootr's own `globals.css` overrides were written for), not the newly-published canonical `1.0.0-beta.1` editor with its already-fixed, already-tested responsive toolbar. This is category (b) from `CLAUDE.md`'s bug-triage rule — a stale-build/environment artifact — not a genuine regression or a new gap in the prior fix.

## Fix

Not a code fix. Killed Sootr's stale `next dev` process (PID 28245, running since 2026-08-21), cleared `.next` build cache, and started a fresh dev server so it resolves against the just-installed `1.0.0-beta.1` packages.

**Not yet independently re-confirmed against the live authenticated app** (no Chrome extension connection available in this session to navigate Sootr's real, auth-gated block-editor route at the exact reported width) — the fresh dev server starts cleanly, but the actual visual re-check at ~700-800px in the real split pane still needs to be done by loading the real page after this restart.

## Recommendation for Sootr's own maintainers (separate from this fix, not blocking)

- `app/globals.css`'s four `.smartrte-container > div:first-child > div:first-child`-based rules are dead code against the current editor and should be rewritten against real, stable selectors (`.smartrte-container .srte-toolbar`, `.smartrte-container .srte-toolbar-group`) if the underlying intent (extra wrap safety margin) is still wanted — though the package's own native responsive toolbar (mobile tier + wide-viewport promotion) should make most of this unnecessary now.
- `app/[...]/blocks/[blockId]/page.tsx`'s editor panel `minWidth: '25%'` is a relative floor, not a pixel floor — on a narrow-enough window, 25% of the row can still be less than the toolbar's natural per-group content width. Not proven to cause this specific report (mechanically equivalent to any other narrow width, which the sweep found clean), but worth hardening to a fixed pixel floor (e.g. `minWidth: '420px'`) for defense in depth.
- **General process recommendation**: restart the Next.js dev server after any `smartrte-react`/`smartrte-core` version bump — this is the second time in this project's history a long-lived dev server has produced a "still broken" report for already-fixed code (the first being the Vite playground's own instance, `stale-dist-build-confusion.md`).
