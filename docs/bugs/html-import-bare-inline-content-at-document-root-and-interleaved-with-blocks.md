# HTML import: bare inline content sitting at the document root (or interleaved with blocks anywhere) routed to `[Unsupported: ...]` instead of parsed

**Status:** Fixed
**Area:** core / `list/formats.ts`'s HTML parser (`parseCanonicalListHtml`, and `parseBlock`'s blockquote/td/li cases)
**First reported:** 2026-09-06, "Some old sootr content is not proper rendering to editor", with the live rendered DOM attached showing dozens of `[Unsupported: span]` placeholders and one `[Unsupported: b]`. Two real source HTML exports were shared directly (a legacy-editor export with bare `<span>`/`<b>` siblings of empty `<p>` tags, and an earlier-generation export using `<div>` wrappers around the same bare inline runs, including one with a bare `<span>` immediately followed by a bare text node inside a `<blockquote>`).
**Related files:** `docs/bugs/html-import-span-and-div-wrapped-content-lost.md` (the closely related prior fix this one directly extends and partly supersedes the scope of - that fix added a "direct inline content" fallback to `blockquote`/`td`/`li` specifically, but never to the actual document-root parser itself, which is where this report's content broke).

## Root cause

`parseCanonicalListHtml` (the top-level HTML→model entry point, also used by `parseClipboardPayload` for paste, and by `defaultValue`/`initialValue` for loading a document into the editor) called `parseBlockList(elementChildren(source))` with **no fallback at all** for inline content sitting directly at the document root - unlike the prior fix's `blockquote`/`td`/`li` cases, which at least had a "collect every direct-inline child into one paragraph, prepend it" fallback. A legacy-editor export with bare `<span style="...">line</span>` or `<b>...</b>` elements sitting directly as siblings of (often empty) `<p>` tags - confirmed directly from two real exports the user provided - hit `parseBlock`'s generic "unrecognized tag" fallback for every such element, producing one `unknown` node per line, rendered as `[Unsupported: span]`/`[Unsupported: b]`.

The prior fix's "collect all direct-inline children into ONE paragraph, unshift" strategy (still used by `blockquote`/`td`/`li`) was also insufficient for this content: real legacy exports interleave many separate inline lines *between* real blocks (a `<blockquote>`, several `<div>`-wrapped lines, another `<blockquote>` at the very end) - collecting them all into one paragraph would have silently reordered content to the front and merged unrelated lines together.

## Fix

Replaced `parseBlockList` with `parseMixedBlockContent(nodes, blockTags)`, used by the document root, `blockquote`, `td`, and `li`:

- Walks children in order, grouping each **run** of consecutive non-block-like nodes into its own synthetic paragraph in place, preserving both the surrounding blocks' order and which inline runs were actually adjacent in the source - not a single blob collected from the whole container.
- A small `GENERIC_INLINE_TAGS` list (`span`, `strong`/`b`, `em`/`i`, `u`, `s`/`strike`/`del`, `code`, `sup`, `sub`, `a`, `br`) is deliberately narrow: only these unambiguous inline-formatting tags get reinterpreted as text via `textWithMarks`. `a` gets a small special case (tried as a block first, for `parseBlock`'s pre-existing "`<a>` wrapping only an `<img>`" → block-image unwrap; only falls back to inline link text if that doesn't apply).
- **Anything else unrecognized** (an arbitrary/custom element, e.g. a host's own safe custom widget surviving the clipboard security boundary) still goes through `parseBlock`'s own "unknown" round-trip-preserving fallback exactly as before - this was a real regression caught mid-fix by `clipboard/pipeline.test.ts`'s "preserves a sanitized safe custom element as an unknown node" test, since an earlier, broader version of this fix reinterpreted *any* non-block tag as inline text, silently flattening custom elements instead of preserving them.
- A UI-only element (e.g. a checklist item's check-control `<button data-smart-ui="...">`) is now explicitly dropped at the very top of `parseMixedBlockContent`, matching `textWithMarks`'s own existing `isEditorUiNode` guard - caught by `formats.test.ts`'s "excludes checklist editor UI controls from canonical content" test, since the new `parseBlock`-fallback path for genuinely-unrecognized tags doesn't have that guard on its own.
- A text node that is **entirely whitespace** (a newline/indentation between block-level tags in pretty-printed source HTML, confirmed directly in the `word-macos-clipboard` fixture's own raw HTML) no longer produces a spurious empty-looking paragraph, matching ordinary browser whitespace-collapsing between block elements - a run with any real text or non-text child (an atom, a `<br>`) is kept in full, including any whitespace mixed into real content.

## Regression coverage

- `packages/core/src/foundation/list/formats.test.ts` - new test using a permanent fixture (`packages/react/e2e/fixtures/sootr-legacy-editor-bare-inline-export.html`, the second, `<div>`-wrapped real export the user provided): zero `unknown` nodes, every line of real text present, bold marks survive on bare root-level `<b>` text, both blockquotes (including the deeply nested trailing one) survive as real blocks, and the trailing image survives as a real atom.
- Directly verified (not just via the automated test) against **both** real files the user attached, using the built package directly: zero `unknown` nodes and every line of text recovered in the correct order for each.
- `packages/core/src/foundation/clipboard/pipeline.test.ts`'s pre-existing custom-element-preservation tests and `formats.test.ts`'s checklist-UI-exclusion test - both briefly broke mid-fix (see above) and are now green again, confirming the narrower `GENERIC_INLINE_TAGS`/UI-node-guard design doesn't regress either.
- `packages/core/src/foundation/clipboard/corpus.test.ts` - one locked structural hash (`word-macos-clipboard.clipboard.json`) changed as a direct, verified consequence of the whitespace-only-run suppression (inspected the fixture's raw HTML directly to confirm real indentation whitespace between `<td>` and its `<p>`, not an assumption from the diff alone) - updated with an explanatory comment, not silently accepted. `excel-clipboard`/`google-sheets-clipboard` hashes were also confirmed byte-identical to their pre-fix output via a direct before/after structural dump, despite initially appearing to change mid-fix (an intermediate, since-corrected version of this fix had a real regression there too - see below).
- Full core suite (739/739) and full react unit suite (151/151) pass with no other changes. Full react e2e suite run in progress at time of writing.

## Errors made and corrected during this fix (kept for the same reason `toolbar-wide-promotion-fires-on-viewport-width-not-container-width.md` keeps its own correction)

1. First attempt used a hand-picked `blockTags` allowlist for the document root modeled on `blockquote`'s own list, missing `"a"` - broke the existing "`<a>` wrapping only an `<img>`" block-image unwrap tests. Fixed by trying `parseBlock` first for `<a>` specifically.
2. Second attempt classified *any* non-block, non-transparent-container tag as inline-reinterpretable - broke `clipboard/pipeline.test.ts`'s custom-element-preservation tests (an unrecognized custom element's text was silently extracted instead of preserving the element as `unknown`). Fixed by introducing the narrow `GENERIC_INLINE_TAGS` allowlist and keeping the `parseBlock`-fallback path for everything else.
3. Third attempt's `parseBlock`-fallback path didn't check `isEditorUiNode` first - broke `formats.test.ts`'s checklist-UI-exclusion test (a check-control `<button>` was preserved as an `unknown` node instead of silently dropped). Fixed by adding the same guard `textWithMarks` already has, at the top of `parseMixedBlockContent`.
4. `GENERIC_INLINE_TAGS` initially omitted `"br"` - broke the `excel-clipboard` corpus hash (a bare `<br>` inside a table cell, not wrapped in `<p>`, was misrouted to `parseBlock`'s generic fallback instead of becoming a `hard_break`). Fixed by adding `"br"` to the list; verified byte-identical structural output to the pre-fix parse afterward.
