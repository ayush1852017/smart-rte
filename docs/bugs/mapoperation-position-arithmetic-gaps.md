# `mapOperation` had multiple real position-arithmetic bugs, undetected because it had zero production callers

**Status:** Fixed (findings 1-4: 2026-08-27; finding 5, the required mergeNode/splitNode follow-up: 2026-08-28)
**Area:** core / operations.ts (`mapOperation`, `mapPosThroughOperation`)
**First reported:** 2026-08-27, found during Phase 12b-client's pre-work (§1.1: "confirm `mapOperation` actually transforms correctly against everything that exists today, not just what existed when it was written").
**Related files:** `packages/core/src/foundation/operations.ts`, `packages/core/src/foundation/collab/transform.ts` (the only production caller, added this phase), `packages/core/src/foundation/collab/rebase.property.test.ts`

## Symptom

None reported by a user - this was found proactively. `mapOperation(operation, through)` is the operational-transform primitive the Phase 8c collab-readiness gate's assertion 5 requires ("every operation implements `map(op, otherOp)`"), and its own test coverage (`foundation.test.ts`) asserted every operation type could be mapped through a fixed "through" operation *without throwing*, and that the result's `.type` was preserved - but never asserted the resulting *position* was actually correct for a realistic concurrent pairing. `grep`-ing the whole codebase found `mapOperation` had **zero production callers** anywhere before this phase - it existed purely to satisfy the gate's assertion, never actually exercised.

## Reproduction

Confirmed via seeded-PRNG TP1 (Transformation Property 1) convergence tests - apply A then (B transformed through A), and apply B then (A transformed through B), from the same base state, and assert both produce the *same* document. All four were found this way, not by inspection:

1. Two concurrent `insertNode` operations at the same parent, non-tie offsets (e.g. offsets 2 and 5 into an 8-child array) diverged depending on transform order.
2. Two concurrent `removeNode` operations targeting the *identical* node (or a `removeNode`/`replaceNode` pair at the same slot) corrupted the document - the second one's stale `.node`/`before` payload no longer matched what was actually there.
3. An `insertNode`-vs-`removeNode` pairing at a *numerically coincidental* offset (insert's gap-offset happening to equal remove's occupied-slot-offset) was initially "fixed" by conflating the two - which broke ordinary insert-vs-remove pairs that were never actually ambiguous.
4. The exact-tie bias override (added this phase for authorId-based insert ordering, see the companion doc on conflict-classification decisions) was initially applied unconditionally to every position pair, which corrupted `removeNode`'s target when transformed through a concurrent `insertNode` at a coincidentally-equal offset - `removeNode` identifies its target by node identity, not by an ordering competition, so "which one sorts first" has no meaning there.
5. **(2026-08-28, required follow-up)** `mapOperation` had no explicit handling for a native `mergeNode`/`splitNode` transforming through a *concurrent* `mergeNode`/`splitNode` - exactly the operation pair Phase 12a's `mergedInto`/`retiredInto` merge-orphan work was built around. Three separately-verified, distinct outcomes via direct concurrent-case construction (not generic sweeps - see Regression coverage below for why generic coverage could never have found this):
   - **Case A (mergeNode vs. mergeNode retiring adjacent siblings): genuine TP1 violation.** Crashed ("mergeNode requires structurally compatible siblings and the exact split offset") in one transform direction, silently produced a *different* document in the other.
   - **Case B (mergeNode vs. splitNode targeting the exact node being retired): converges correctly**, confirmed *and understood* (not just observed) - see Root cause below.
   - **Case C (splitNode vs. splitNode at the identical boundary): genuine TP1 violation** - a "swapped identity" divergence (whichever split ends up empty differs by transform order), a tie with no tie-break, not a staleness problem.
   - **Quick moveNode re-check (per the same follow-up's item 5):** no new gap found. A moveNode's own carried content (a concurrent edit *inside* the moved node) and unrelated concurrent edits elsewhere both converge correctly, and same-node concurrent moves still conflict as already established (`concurrent-rebase-non-transformable-conflicts.md`) - moveNode's existing broad conflict rule and descendant-redirect logic already cover this correctly.

## Root cause

`SmartOperation`'s `.pos`/`.from`/`.to` fields reuse the same `{path, offset}` shape (`SmartPos`) for at least three structurally different meanings, and `mapPosThroughOperation`/`mapOperation` are generic, type-blind position arithmetic with no way to know which convention a given `pos` follows:

- **Occupied-slot reference** (`removeNode.pos`, `replaceNode.pos`, `moveNode.from`/`.to`): "the node currently at this index."
- **Gap reference** (`insertNode.pos`): "the boundary before this index" - numerically identical to an occupied-slot offset at the same position, but referring to something different.
- **Deep/nested reference** (`insertText.pos`, `deleteText.pos`, `setNodeAttributes.pos`, etc.): a position potentially several levels below the compared path, where prefix-based containment checks (already correct in the original code) apply.

Bug 1 (sibling `insertNode` shift): `removeNode`'s branch already special-cased "same parent, greater offset -> shift", but `insertNode`'s branch only special-cased the exact-tie case, falling through to `shiftPath` for everything else - which only shifts a position *strictly deeper* than the insertion point, never a same-depth sibling.

Bug 2 (exact-match not detected): the reverse gap - `removeNode`/`replaceNode`'s "target no longer exists" detection only checked the deep-prefix case, never a same-depth sibling reference at the identical slot.

Bug 3/4: fixing bugs 1 and 2 by adding same-depth-equal-offset checks *inside* the shared, type-blind `mapPosThroughOperation` was itself wrong, because it can't distinguish which convention `pos` follows - a coincidental offset match between an occupied-slot reference and a gap reference (or a text-offset from an unrelated `insertText`) is not a real "same target."

**Finding 5, Case A**: `mergeNode.splitOffset` is a *child-count* payload (`applyOperation` validates `splitOffset === left.children.length`, not a character count as originally assumed while investigating), analogous to `deleteText.text` - it records an expectation about the survivor's content that only stays valid if nothing else changes that survivor's identity. `mapPosThroughOperation`'s mergeNode-as-through branch tracks a single explicit position (the operation's own `.pos`/`.from`); an ordinary sibling-index shift correctly keeps a *retiring* target's own identity reachable, but has no way to notice that a *different*, only-implicitly-referenced neighbor (the "left" node at `offset - 1`) changed identity underneath it.

**Finding 5, Case B (why it's safe)**: `mapPosThroughOperation`'s mergeNode-as-through branch has an explicit case for a position whose *own full path* exactly equals the retired node's path (`operations.ts` ~line 400) - this is precisely the shape a `splitNode` targeting that exact node has (its target-container reference *is* a full path, unlike mergeNode's own parent+index `.pos`). That case redirects into the survivor with genuinely recomputed offset arithmetic (`splitOffset + pos.offset`), not a stale cached payload - it's real position math, so it stays correct regardless of what mutated the survivor.

**Finding 5, Case C**: `mapPosThroughOperation`'s `splitNode` branch had no case at all for `pos.offset === operation.pos.offset` (only `>`), so the tied position fell through to the function's unchanged-passthrough default in both directions - not a staleness problem like Cases A/1/2, but the same missing-tie-break class as the original insertNode/insertText fixes.

## Fix

- **Bug 1**: `mapPosThroughOperation`'s `insertNode` branch gained the missing same-parent, greater-offset case, mirroring `removeNode`'s existing pattern exactly.
- **Bug 2**: relocated to `mapOperation` itself (not `mapPosThroughOperation`), scoped precisely to `removeNode`/`replaceNode` vs. `removeNode`/`replaceNode` at the identical slot - the one call site that actually knows both operations' real types, rather than the shared, type-blind position mapper.
- **Bug 3/4**: `mapOperation` gained an optional `tieBreakBias` parameter, but its default-overriding behavior is restricted to `isGenuineTie = operation.type === through.type && (operation.type === "insertNode" || operation.type === "insertText")` - every other pairing always uses the original hardcoded bias (1), regardless of authorship, since only a same-kind insertion race is a genuine ordering competition.
- **Finding 5, Case A**: flagged as an explicit conflict (`collab/transform.ts`'s `transformOperation`, finding/decision 3 in its own doc comment) whenever a concurrent operation occupies either of a mergeNode's left or right slots - restricted to operations using the same "parent+index, occupied slot" convention mergeNode's own `.pos` does (`removeNode`, `replaceNode`, another `mergeNode`'s own slots), explicitly excluding `insertNode` (gap semantics, not slot semantics - confirmed via a property test that a plain insertNode *before* a merge's survivor converges fine and must not be flagged) and excluding `splitNode`/deeper references (already safely redirected, per Case B). No general fix attempted, for the same reason as findings 1-4's siblings: `mapOperation` has no document access to safely recompute a stale `splitOffset`.
- **Finding 5, Case C**: `isGenuineTie` (operations.ts) extended to include `splitNode`, and `mapPosThroughOperation`'s `splitNode` branch's existing shift condition extended from `pos.offset > operation.pos.offset` to also cover the tie (`|| (pos.offset === operation.pos.offset && bias > 0)`) - the identical pattern already used for `insertNode`/`insertText`.
- Also confirmed **not** a bug: non-adjacent concurrent `mergeNode` pairs (no shared slot) converge correctly without needing conflict treatment, and `splitNode` vs. `splitNode` at *different* (non-tied) offsets on the same node converges correctly via the pre-existing shift arithmetic - the fixes above are scoped to the precise failure conditions, not broadened defensively.

## Regression coverage

`packages/core/src/foundation/collab/rebase.property.test.ts`: 1,000-case seeded sweeps (seeds `0xC0FFEE`, `0x5EED7EA`) covering `insertNode`/`removeNode`/`moveNode` and `insertText`/`deleteText` pairs, asserting exact TP1 convergence (not just "doesn't throw"). `packages/core/src/foundation/collab/dispatch-rebase.test.ts` exercises the same fixes through the real `FoundationEditor.dispatch` integration point, not just the pure function. A dedicated `describe` block adds Cases A/B/C plus two refinement cases (non-adjacent merge, mergeNode-vs-unrelated-insertNode) as permanent, named tests - **not left to generic sweep coverage**, since the sweep's own operation generator only ever produces `insertNode`/`removeNode`/`moveNode` and could never have generated a `mergeNode`/`splitNode` case regardless of iteration count, the same lesson as the `addMark`-boundary finding but stronger (there, the right operation *types* were already in the sweep and only the exact offset was missing; here the types themselves were entirely absent). Full core suite: 720/720 (was 704 before this phase), react 132/132, lint clean, full e2e 468/477 (2 pre-existing unrelated Firefox flakes, 7 skipped) - zero regressions.
