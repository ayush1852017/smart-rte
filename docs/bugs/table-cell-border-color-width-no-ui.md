# Table cell border colour/width had no UI - the "written, never rendered" pattern, but inverted (written AND rendered, never settable)

**Status:** Fixed
**Area:** table / react / docx
**First reported:** 2026-08-30, "Codex prompt — table cell border width/color: investigate then implement"
**Related files:** `table-insert-row-column-no-style-inheritance.md` (explicitly named `borders` as an already-inheriting cell-style attribute), `color-picker-redesigned-drag-first-no-apply-button.md` (the color picker component reused here unmodified)

## The finding, stated first (per the report's own instruction)

**This was a UI-only gap, not a missing model capability** - `table_cell.attrs.borders` already existed in the schema, was already applied live by the renderer, and already round-tripped through HTML import/export. It was only ever reachable by pasting HTML that already had cell borders (or by a raw `runtime.executeOperations` call bypassing the UI entirely) - the editor's own toolbar/context-menu had no control that ever wrote to it. Confirmed by setting it via a direct command call before touching any UI: it rendered correctly immediately.

One genuine gap was found and fixed as part of verifying export fidelity: **DOCX export only ever special-cased `borders === "none"`** (removing the table's default grey border) and silently dropped any real width/colour value, which would have made this a sixth "written, never rendered" instance the moment the new UI made real values reachable. Fixed alongside the UI work - see below.

## Investigation

- `packages/core/src/foundation/table/schema.ts:27`: `borders: optionalString` on `table_cell` - already present.
- `packages/core/src/foundation/table/commands.ts:28`: `CELL_STYLE_ATTR_KEYS = ["background", "borders", "textColor", "verticalAlign"]` - `borders` is already one of the four attrs `insertTableRowCommand`/`insertTableColumnCommand` inherit onto new cells (per `table-insert-row-column-no-style-inheritance.md`), and already settable generically via the existing `setTableCellAttributesCommand` (`table.setCellAttributes`) - no new command needed.
- `packages/core/src/foundation/surface/renderer.ts:283`: `if (node.attrs?.borders) element.style.border = String(node.attrs.borders); else element.style.removeProperty("border");` - already applied to the live DOM verbatim, confirmed by setting the attribute directly (bypassing all UI) and observing the rendered cell's border change immediately.
- `packages/core/src/foundation/list/formats.ts:139,459-463`: already both written (`border:${...}` in HTML export) and parsed back (`cellAttrs.borders = borders` from a pasted `<td style="border:...">`) - full HTML round-trip already worked.
- `packages/core/src/foundation/formats/docx/export.ts:182` (pre-fix): `cell.node.attrs?.borders === "none" ? borderNone : ""` - the **only** gap found. A real value like `"2px solid #ff0000"` matched neither branch and produced no override at all, leaving the cell with the table-wide default border (`w:tblBorders`, solid grey `D1D5DB`) in the exported `.docx`, silently discarding whatever was actually set.
- No existing UI control anywhere (toolbar, table context menu, table plugin contributions) ever wrote to `borders` - confirmed via search across `CanonicalAuthorityEditor.tsx` and `table/plugin.ts`.

**Scope** (per the report's explicit ask): `borders` lives on `table_cell`, not `table_row` or `table` - so the correct UI granularity is **per-selected-cell(s)**, identical to the existing background/text-colour cell controls (`setTableCellAttributesCommand` applies uniformly to `scope.cellIds`, which is one cell for a single click or every cell in a dragged range). Not per-row or per-table.

## Fix

**Model/command/renderer/export**: only the DOCX export gap needed a real fix (`packages/core/src/foundation/formats/docx/export.ts`): added `cellBorderXml(value, borderNone)`, parsing the one shape the new UI itself writes (`"{width}px solid {hex|rgb}"`) into real OOXML `<w:tcBorders>` (`w:sz` in eighths-of-a-point, `w:sz = px * 6`, matching this codebase's existing px→twips convention of `px * 15` for column widths/row heights, i.e. 1px = 0.75pt = 6 eighths-of-a-point). Arbitrary pasted CSS border shapes that don't match (e.g. `dashed`, non-hex colours) fall through to no override, same as before this function existed - not a regression, since nothing but `"none"` was ever handled here.

**UI** (`packages/react/src/components/CanonicalAuthorityEditor.tsx`):
- `composeBorderShorthand(widthPx, hex)` / `parseBorderShorthand(value)` - compose/parse the one shape this UI writes; a `BORDER_WIDTH_PRESETS` array (Thin=1px, Medium=2px, Thick=4px).
- **Border width**: a `<select>` embedded directly in the "Table tools" toolbar dropdown, mirroring the exact pre-existing pattern of "More list tools"' embedded "List preset" `<select>` rather than inventing a new control shape. Chosen over a raw numeric input because (a) it matches an already-established in-dropdown pattern in this exact codebase, and (b) discrete presets match "common editor conventions" (Word/Google Docs both offer discrete border-weight choices, not freeform px entry). Applying a width reads the cell's *current* border colour (or black, if unset) and recomposes, so it never clobbers an already-chosen colour.
- **Border colour**: reuses `ColorPickerPopover` completely unmodified (per the report's explicit instruction) - same live-preview-while-dragging/typing, commit-on-dismiss, Discard-reverts-only model already hardened for text/background colour. `colorPopover.target`'s cell variant gained a `"borders"` attr option carrying a captured `borderWidthPx` (read once at open time, same "capture at click time, don't re-resolve live" pattern already used for the cell scope itself - see `color-picker-cell-target-recomputed-live-race.md`); `applyColorToTarget` composes `width+hex` into the shorthand only for this attr, leaving the background/textColor branches untouched.
- A new "Border colour" `<ToolbarMenuItem>` sits in "Table tools" (toolbar dropdown) and a new "Cell border colour" item sits in the right-click table context menu, mirroring "Cell background colour"/"Cell text colour" exactly. Width has **no** context-menu equivalent - `ContextMenu.tsx`'s `ContextMenuItem` is a flat `{id, label, onSelect}` shape with no embedded-control support (confirmed by reading its interface), so a preset `<select>` has nowhere to live there; it's toolbar-dropdown-only, which is still always reachable whenever a cell is selected.
- `ColorBucket`/`colorBucketFor`/`recentColors` extended with a third `"border"` bucket, parallel to the existing `"text"`/`"background"` ones - border colours get their own independent 4-slot recent-colour history, not mixed with text/background.
- New `cellBorder` icon (`Square`, from `lucide-react`) added to `ToolbarPrimitives.tsx`'s icon map - no existing icon represented "a cell border."

## Addendum (2026-08-30): per-side control, border style, and a combined popover replace the width-select + colour-item UI above

Immediate user feedback after the fix above: the context menu had no width control at all (only the toolbar dropdown did), and a request for "border fill position" (which sides get a border) and a border-style option. The per-side request is a genuine model extension - `borders` was always ONE uniform CSS border shorthand applied identically to all four sides (`element.style.border = ...`), so "top border but not left" had no attribute to hold it. Confirmed via `AskUserQuestion` before building: per-side control (not uniform-only), styles limited to solid/dashed/dotted, and one combined "Border options" popover (not separate width/colour controls) were all confirmed as the wanted scope.

**Schema** (`packages/core/src/foundation/table/schema.ts`): added `borderTop`/`borderRight`/`borderBottom`/`borderLeft` (`optionalString`) to `table_cell`, alongside the existing `borders`. `borders` stays as the legacy uniform fallback - a side without its own override still renders/exports using it, so old documents and simple HTML-shorthand pastes are unaffected.

**Renderer/modelDom** (`surface/renderer.ts`, `modelDom.ts`): apply the uniform `borders` value first (or remove it), then apply/remove each per-side longhand (`border-top` etc.) - setting a CSS longhand after the shorthand overrides just that one side, leaving the shorthand's effect on the other three untouched. This is genuine CSSOM behavior, confirmed working in all three browsers via the e2e test.

**HTML export/import** (`list/formats.ts`): export emits `border-top:`/etc. declarations for any set per-side attr, after the uniform one; import now also parses `border-top`/`border-right`/`border-bottom`/`border-left` from pasted `style`, not just the generic `border` shorthand. This turned out to matter far beyond the new UI - **Word, Google Docs, and Google Sheets clipboard captures all express cell borders as separate `border-top`/`border-right`/`border-bottom`/`border-left` declarations, never the uniform `border` shorthand** (confirmed by inspecting the captured fixture HTML directly) - meaning paste from any of these three sources previously discarded ALL cell border styling silently. `corpus.test.ts`'s three affected fixture hashes were updated with a comment explaining why (a genuine fidelity improvement, not a regression).

**DOCX export** (`docx/export.ts`): `cellBorderXml` reworked to resolve each of the four OOXML `<w:tcBorders>` sides independently (`cellSideBorderXml`, per-side attr falling back to the uniform `borders` value), and to map border style (solid/dashed/dotted) to its own OOXML `w:val` keyword instead of always `"single"`.

**UI**: the previous "Border width" `<select>` + "Border colour" `<ToolbarMenuItem>` (in the toolbar dropdown) and "Cell border colour" context-menu item are all **removed**, replaced by a single new `TableBorderPopover.tsx`: a small side-selector box (4 independently toggleable edge buttons, plus "All sides"/"No border" shortcuts), a style `<select>` (solid/dashed/dotted), a width `<select>` (the same Thin/Medium/Thick presets), and a colour swatch that opens the existing `ColorPickerPopover` **unmodified** as a nested popover. One style/width/colour choice applies to whichever sides are toggled on - not four fully independent per-side style choices, matching how real border dialogs (Word, Google Docs) default to this simpler mode. Reachable from both "Table tools" (toolbar dropdown, "Border options") and the table context menu ("Cell border options") - both entry points now expose every control, closing the original "width isn't in the context menu" gap.

Unlike the plain colour picker's discard-only model, this composite dialog commits only via an explicit **Apply** button (Cancel/Escape/outside-click all revert) - a deliberate difference: `ColorPickerPopover` governs one field, where "any dismissal but Discard commits" is safe; this dialog assembles four independent fields together, where an accidental outside click mid-adjustment silently committing a half-configured border would be a worse default. Live preview still works throughout (every side toggle, style pick, width pick, and colour drag/type fires an immediate preview via the same checkpoint-then-reapply pattern `previewColor` already used) - only the final "make it permanent" step waits for Apply.

One implementation subtlety worth recording: the nested `ColorPickerPopover` is a DOM *sibling* of `TableBorderPopover` (both are independent `position:fixed` overlays), not a descendant - naively reusing `TableBorderPopover`'s own outside-click-dismiss check (`rootRef.contains(target)`) would have treated every click inside the nested colour picker as "outside," canceling the whole dialog while the user was just trying to drag the hue slider. Fixed by explicitly exempting clicks inside `[data-srte-color-popover="true"]` while it's open, and by suppressing the outer popover's own Escape handler while the nested picker is open (so Escape dismisses the colour picker first; a second Escape closes the whole dialog).
