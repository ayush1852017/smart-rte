# Toolbar wide-promotion fired on browser window width, not the editor's own rendered width — broke split-pane hosts

**Status:** Fixed
**Area:** react / theme.ts (CSS) — a real regression introduced by `toolbar-priority-collapse-fixed-threshold-no-wide-promotion.md`'s own fix
**First reported:** 2026-08-31, "Codex prompt — toolbar breaks at real narrow (split-pane) widths, not just mobile" — real Sootr screenshot, editor in a ~750-800px split pane next to a Web/Flutter Preview panel inside a wide (≥1440px) browser window. Symptoms: toolbar labels mashed together with zero spacing ("Italic"/"Underline" rendering as "ItalicUnderline"), toolbar unresponsive to clicks, and (separately, see below) fixed editor height with no internal scroll.
**Related files:** `packages/react/src/theme.ts`, `packages/react/e2e/canonical-toolbar-routing.spec.ts`, `docs/bugs/toolbar-priority-collapse-fixed-threshold-no-wide-promotion.md` (the fix this regressed), `docs/bugs/sootr-toolbar-mashed-labels-stale-dev-server.md` (this investigation's own first, wrong attempt), `/Users/ayushbajpai/Developer/sootr-vetkai/app/globals.css` (a second, unrelated dead-selector bug found and fixed alongside this)

## Investigation

A first pass (`sootr-toolbar-mashed-labels-stale-dev-server.md`) incorrectly concluded this was a stale Next.js dev-server process, not a package bug — a synthetic sweep of the standalone playground across 340-2300px found zero overlap in any of three engines, and Sootr's own `next dev` process really had been running 10 days stale. That conclusion was falsified when the user reloaded after the dev-server restart and the identical symptom persisted, now unambiguously against the new editor (the screenshots showed "Version history"/"Insert formula"/"Special characters" - labels that only exist in the canonical editor, proving the new code was genuinely running).

**The missed variable**: every synthetic test up to that point used `page.setViewportSize()`, which changes the *browser window* and the editor's own rendered container width **simultaneously and identically** — a plain top-level playground page can never separate them. Sootr's real layout does exactly that: the editor sits in a resizable pane next to a preview panel, so the window can be wide while the editor's own box is narrow. Building a repro that constrained the editor's container independently of the viewport (wrapping the rendered `.srte-root.srte-editor` in a fixed-width div, window left wide) reproduced the exact screenshot pixel-for-pixel on the first try.

**Root cause**: `toolbar-priority-collapse-fixed-threshold-no-wide-promotion.md`'s fix added, for both its breakpoints (639px mobile tier, 1440px wide-promotion tier), a plain `@media` rule *alongside* the correct `@container srte-editor` rule — apparently as a belt-and-suspenders duplicate, without considering that the two can disagree. `.srte-editor` already declares `container: srte-editor / inline-size` on itself (`theme.ts:80`), so `@container srte-editor (min-width: 1440px)` always correctly reflects this specific editor instance's real rendered width, in any host layout. But `@media (min-width: 1440px)` only ever checks the *browser window* — in Sootr's split pane, the window was ≥1440px even though the editor's own box was ~750-800px, so the `@media` rule alone was enough to promote all 9 wide-viewport tools (Superscript, Subscript, Text colour, Background colour, Font size, Font family, Remove link, Insert formula, Special characters) into the main toolbar row, cramming a group meant for 4 buttons with 6-9, well past what the actual available width could hold. `.srte-toolbar-group`'s `min-width: 0` (needed so *whole groups* can wrap on the outer `.srte-toolbar`) let the overloaded group's own buttons shrink and visually overlap instead of the group wrapping cleanly, producing the mashed-together labels — confirmed via `scrollWidth` vs. rendered-width mismatches on the affected buttons.

**The "unresponsive toolbar" report is the same bug, not a separate one**: with buttons visually overlapping, click coordinates land on whichever element the browser's hit-testing picks at that point, not necessarily the one the label makes it look like. Confirmed directly: at the exact repro width (800px container inside a 1600px window), clicking "Bold"/"Italic" produced no `<strong>`/`<em>` before the fix and worked correctly immediately after it, with no other change.

## Fix

`packages/react/src/theme.ts`: removed both plain `@media (max-width: 639px)` and `@media (min-width: 1440px)` blocks entirely, keeping only their `@container srte-editor` counterparts (which were already present and already correct — the `@media` versions were pure duplication, never load-bearing for any legitimate case). Container queries have full support across all three of this project's target engines, so there is no compatibility reason to keep a viewport-based fallback for a component-level responsive threshold.

## A second, unrelated bug found and fixed in Sootr's own code while investigating the "no scroll" report

Sootr's `app/globals.css` had `.block-editor-rte > .smartrte-container > .srte-editor > div:has(> [contenteditable])` — meant to give the editor's scrollable content area `flex: 1 1 auto; min-height: 0; overflow-y: auto`. This selector expects the contenteditable element to be a further-nested child *inside* a wrapper div, but the current canonical editor's contenteditable surface *is itself* `.srte-editor[contenteditable]` (a direct child of the outer `<section class="srte-root srte-editor ...">`, confirmed via direct DOM inspection) — written against the old DOM-authoritative editor's shape, matching nothing in the new DOM. Fixed by changing the selector to `.block-editor-rte .srte-editor[contenteditable]` directly. Also fixed the same dead-`div:first-child` pattern in the adjacent height/flex rule (`.block-editor-rte > .smartrte-container > div:first-child` → `.block-editor-rte > .smartrte-container > .srte-editor`), for the same reason (the outer `.smartrte-container`'s real first child is a `<section>`, not a `<div>`).

Sootr's `globals.css` also still has four older `.smartrte-container > div:first-child > div:first-child`-based rules (commented "Allow the toolbar to wrap on smaller screens") that are similarly dead against the current DOM — confirmed via direct `querySelector` (`.smartrte-container > div:first-child` returns `null`). Left as-is since they're inert, not causing harm; flagged as cleanup for Sootr's maintainers, not fixed here to avoid unrequested scope creep on a file this package doesn't own.

## Regression coverage

New `test.describe("toolbar priority-collapse: container width, not viewport width", ...)` in `canonical-toolbar-routing.spec.ts`:
- Wide window (1600px) + split-pane container (800px, the reported width): promotion stays off, zero overlap/shrink, and a functional check (select text, click Bold, assert `<strong>` — the exact "unresponsive toolbar" scenario) all pass.
- Wide window (1600px) + extreme split-pane container (300px): correctly falls to the mobile tier despite the wide window (the inverse direction of the same bug class — a window-based `@media` would also fail to *demote* correctly here).
- Continuous sweep, 340-2300px container width inside a fixed 2400px window, every 80px: zero overlap or content-squeeze at any width — the property-style, continuous-range check the original report specifically asked for, since a handful of discrete snapshot widths is exactly what let the original fix's own regression suite miss this (every one of its tests resized the viewport, which can never diverge from container width in a single-page test).

All 9 new tests (3 tests × 3 engines) pass. Full suite after the fix: core 724/724 (unaffected, no core change), react 140/140, `pnpm run lint` clean, full 3-browser e2e run in progress at time of writing (existing wide-promotion tests at 1280/2264px viewport-equals-container widths still pass unchanged, since `@container` alone produces identical results to `@media` whenever the two can't diverge).
