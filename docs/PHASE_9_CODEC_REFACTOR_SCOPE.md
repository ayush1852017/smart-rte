# Scoping the 36-cell `FeatureFormatCodec` refactor

This is a sizing pass only — no implementation. It exists so a future phase-planning pass can schedule this work with real numbers instead of the placeholder "a genuine refactor is needed" note left in `docs/PHASE_9_EXIT_GATES.md` (gate 3) and the Phase 9 completion report (§B.1, §E).

## Background

8 of 44 `FeatureFormatCodec` cells (`images-media` + `formulas`, all 4 formats) have real `parse`/`serialize` functions because `packages/core/src/foundation/atom/formats.ts` already operates on one node at a time. The other 36 cells' real logic lives in five whole-document walkers that resolve every feature together in a single pass. This document inventories those five walkers.

## Walker inventory

### 1. `packages/core/src/foundation/formats/docx/export.ts` — DOCX export

- **Size:** 270 lines. 21 `node.type ===`-style branches across its helper functions (`inlineRun`, `blockXml`, `tableXml`, plus the image/formula/hyperlink-specific helpers).
- **Backs:** `inline-marks`, `colors-fonts-sizes`, `headings-alignment`, `blockquote-code`, `lists`, `checklists` (declares lossy, doesn't emit anything), `tables`, `links`, `images-media`, `formulas`, `special-characters` — all 11 features' DOCX cell (11 of the 36).
- **The actual hard part:** a single mutable `DocxSerializationContext` (`export.ts:61`) carries a `relationships: []` array that every image and hyperlink pushes to, assigning its own `rId` as `` `rId${context.relationships.length + 2}` `` (`export.ts:68`, `:88`) — a monotonically increasing counter that must stay globally sequential across the *entire document*, regardless of which feature triggered it. A standalone "images" codec function can't independently decide its own relationship ID without knowing how many hyperlinks and other images were already assigned earlier in document order. Table export (`tableXml`, `export.ts:157`) separately depends on `occupancyGridFor` for whole-row/table geometry (colspan/rowspan/`gridSpan`/`vMerge`) — inherently table-scoped, not cell-scoped. List numbering (`blockXml`, `export.ts:194`) is comparatively decoupled: `listStyleNumId` (`export.ts:137`) is a static per-style lookup table, not a running counter, so list export is the one sub-feature here that's already close to per-node-shaped.
- **Verdict:** the most tractable of the three non-atom formats. A real fix is to extend `SerializeContext` (currently just `{format}`, `codec.ts:9`) with a mutable relationship-ID allocator specific to DOCX, threaded through every `serialize` call the same way `context` already flows through every helper in this file today. The per-feature split (marks/headings/blockquote-code/tables/links/checklists) is mostly a matter of extracting each existing branch into its own function with that shared context — the branches are already fairly separated by feature, just not exposed as independent functions.

### 2. `packages/core/src/foundation/formats/pdf/format.ts` — PDF export + import

- **Size:** 216 lines, split across two genuinely different problems that happen to share a file:
  - **Export** (`buildPdfPrintDocument`, line 188): walks the document tree and emits HTML per node type for browser printing. Structurally similar in shape to a per-node walker already — reasonably tractable.
  - **Import** (`reconstructPdfPages`, line 77, plus `spanFor`/`lineContent`/`alignmentForLine`): takes a flat list of positioned text items (`x`, `y`, `width`, `height`, `fontFamily` per span) extracted from a rendered PDF page and *synthesizes* document structure from their spatial layout — grouping by vertical position into lines, inferring headings from font size, inferring lists from bullet-glyph prefixes, inferring tables from aligned columns.
- **Backs:** all 11 features' PDF cell (11 of the 36) via the export side; the import side has no real per-feature concept at all (see below).
- **The actual hard part:** PDF import has **no pre-existing node to parse into** — `FeatureFormatCodec.parse(input, ctx) => SmartNode | SmartNode[] | null` presumes there's something identifiable as "this feature's representation" in the input to hand to a specific feature's parser. PDF import instead runs one spatial-clustering pass over the *entire* page and only afterward decides "this cluster is a heading," "this cluster is a table" — the classification is a side effect of whole-page geometry, not a lookup keyed by feature. Splitting this into 11 independent per-feature `parse` functions doesn't just require new plumbing, the way DOCX does — it requires either (a) running the same whole-page clustering pass 11 times filtered to each feature's shape (wasteful, and clusters overlap ambiguously between candidate features by design) or (b) keeping one shared clustering pass and only exposing per-feature classification *after* it, which is arguably not a `parse` function in the sense gate 3 means at all.
- **Verdict:** export side is tractable, similar cost profile to DOCX export minus the relationship-ID complexity (PDF's print HTML has no analogous cross-node ID allocation need). Import side should be treated as a **standing exception**, not a deferred-but-eventually-mechanical task — flag this explicitly in any future scheduling rather than folding it into the same estimate as the other four walkers.

### 3. `packages/core/src/foundation/list/formats.ts` — HTML + Markdown (all features) + DOCX numbering

- **Size:** 580 lines — the largest of the five, and structurally the most cross-cutting despite its name. `serializeBlock` (line 73) and `parseBlock` (line 261) are single mutually-recursive functions that already handle *every* block type in the schema (paragraphs, headings, lists, tables, blockquotes, code blocks — not just lists), because nested content of any type can appear inside a list item and vice versa. `markdownBlock` (line 446) and `blocksFromMarkdown` (line 532) do the same for Markdown. `canonicalListToDocxNumbering` (line 559) is the one genuinely list-scoped piece, feeding both `lists`/DOCX and (via `canonicalListPdfText`, line 579) `lists`/PDF's text projection.
- **Backs:** `inline-marks`, `headings-alignment`, `blockquote-code`, `lists`, `checklists`, `tables`, `links`, `images-media`, `formulas`, `special-characters` HTML+Markdown cells (`colors-fonts-sizes` HTML/Markdown notably does *not* route through here — see marks/formats.ts below) — roughly 18-20 of the 36, the largest single share.
- **The actual hard part:** this is not a threading-state problem like DOCX's relationship IDs — it's that `serializeBlock`/`parseBlock` are *the* HTML/Markdown codec for the whole document today, deeply mutually recursive (a list item's paragraph child can itself contain a nested list, which contains another paragraph, ad infinitum), and already fully tested and working (`full`/`semantic` fidelity for nearly every feature here). Decomposing this into 18-20 independent per-feature functions means extracting a real per-node-type dispatch registry out of what is currently one function per format that happens to have a `switch`-shaped body — technically similar in kind to what DOCX needs, but touching far more surface area, in the single most-exercised code path in the entire format layer (every `<CanonicalAuthorityEditor>` HTML paste/copy, every Markdown import/export goes through this file).
- **Verdict:** the largest and highest-risk unit. Not harder in kind than DOCX's problem, but harder in degree — more branches, more mutual recursion, more existing test surface that a bad extraction could quietly regress. This is also the format pair (HTML/Markdown) where the *practical* benefit of having real per-feature codec objects is lowest, since nothing today actually needs to call "just the list-to-HTML serializer" in isolation — the whole-document functions already serve every real caller.

### 4. `packages/core/src/foundation/marks/formats.ts` — marks' dormant DOCX/PDF layer

- **Size:** 58 lines, 9 type-branches. `canonicalMarksToDocxRuns` and `canonicalMarksPdfText` both take a whole `SmartDocument` and flatten every paragraph's marked runs.
- **Backs:** `inline-marks` and `colors-fonts-sizes` DOCX/PDF cells (4 of the 36) — though note DOCX's actual *production* mark serialization already lives in `docx/export.ts`'s `inlineRun`/`runProperties` (item 1 above); this file's DOCX function is the dormant, test-only twin, not what real exports use (see `docs/bugs/atom-to-docx-described-formulas-as-rendered-images.md` for the general pattern this creates).
- **The actual hard part:** genuinely the smallest here — marks are naturally node-scoped already (a run of marked text doesn't need cross-node state the way relationship IDs or table grids do). The only real design decision is which implementation becomes the source of truth once this is a real codec: the dormant per-feature function, or extracting the equivalent logic already living in `docx/export.ts`'s `inlineRun`. Reusing the production one is almost certainly correct, per the same reasoning as the `atomToDocx` bug this phase found and fixed.
- **Verdict:** smallest and lowest-risk unit, but has a **prerequisite**: decide whether to keep two parallel mark-serialization implementations (current state) or consolidate on the production one before wiring a real codec — doing the codec extraction first would encode the current duplication into the "real" API surface.

### 5. `packages/core/src/foundation/block/formats.ts` and `table/formats.ts` — blocks' and tables' dormant DOCX/PDF layer

- **Size:** `block/formats.ts` 67 lines / 9 branches; `table/formats.ts` 61 lines / effectively table-shaped (one branch, but the table structure itself is the complexity, not type-switching).
- **Backs:** `headings-alignment`, `blockquote-code` (block/formats.ts) and `tables` (table/formats.ts) DOCX/PDF cells (6 of the 36).
- **The actual hard part:** `table/formats.ts`'s `canonicalTablesToDocx` needs the same whole-table geometry (`occupancyGridFor`-equivalent reasoning for spans/merges) that `docx/export.ts`'s `tableXml` already needs — this is real, unavoidable table-scoped state, not just a missing threading mechanism. Note also (found during Phase 9 §3's gate 4 audit) that `table/formats.ts`'s `canonicalTablePdfText` is dead code today — declared, exported, never called from any test or production path (`docs/PHASE_9_EXIT_GATES.md` gate 4 row references this indirectly; tables/PDF fidelity is actually verified via the real `pdf/format.ts` import path instead). `block/formats.ts` is comparatively simple — headings and blockquote/code-block indentation don't need cross-node state.
- **Verdict:** `block/formats.ts` is nearly as tractable as marks. `table/formats.ts` inherits the same table-geometry complexity as DOCX export's table handling, and has its own prerequisite: decide whether to delete the dead `canonicalTablePdfText` or make it real before building a codec around it — wiring a "real" `FeatureFormatCodec.serialize` to a function nothing currently calls would be a strange first caller.

## Proposed split and relative sizing

A feature-by-feature split is natural for **DOCX and PDF-export**, where each walker already has per-feature-shaped internal branches. It is **not** natural for **HTML/Markdown**, where one recursive function already owns every feature at once, and **partially inapplicable** for **PDF-import**, which has no per-feature structure to begin with.

Rough relative sizing (smallest to largest, by combined size + threading-state complexity):

1. **Marks** (`marks/formats.ts` prerequisite decision + DOCX/PDF codec extraction) — smallest. No real cross-node state; the only cost is resolving the dormant-vs-production duplication first.
2. **Blocks** (`block/formats.ts` DOCX/PDF codec extraction) — small, same shape as marks, no duplication prerequisite.
3. **DOCX export, all remaining features** (`docx/export.ts`'s relationship-ID context + list/checklist/table/link/image/formula branches) — medium. One real new mechanism needed (a mutable, threaded relationship-ID allocator), but the branches themselves are already close to separable.
4. **Tables** (`table/formats.ts` + `docx/export.ts`'s table-specific portion) — medium, gated on the same table-geometry threading `docx/export.ts` needs, plus its own dead-code prerequisite.
5. **PDF export** (`pdf/format.ts`'s `buildPdfPrintDocument`) — medium, similar shape to DOCX export minus the relationship-ID problem.
6. **HTML/Markdown, all features** (`list/formats.ts`) — largest by a wide margin: most lines, most mutual recursion, most existing test surface, lowest practical payoff since nothing currently needs these as standalone functions.
7. **PDF import** (`pdf/format.ts`'s `reconstructPdfPages`) — not sizeable as "more or less work" the same way as 1-6; it's a standing architectural exception (see item 2 above). Treat as a research/design question ("should PDF-import fidelity even be expressed as gate 3's per-node `parse` shape") before treating it as an implementation task at all.

## Ordering constraints

- **Marks and blocks have no dependency on anything else** — either could start first, independently, and would validate the general "extract dormant-vs-production duplication, then wire a codec" pattern cheaply before spending it on higher-risk units.
- **DOCX export's relationship-ID context is a prerequisite for images/formulas/links/tables within DOCX specifically** (though images/formulas already have real per-node codecs via the atom layer — this only affects re-deriving *their* DOCX relationship IDs if DOCX export itself gets refactored to route through the codec layer rather than its own bespoke context). Building this context mechanism once benefits every DOCX feature that needs a relationship ID, not just one.
- **Tables (DOCX) and DOCX export's table handling are the same problem** and should not be scheduled as separate units — refactoring one without the other would leave `occupancyGridFor`-based geometry logic duplicated rather than shared.
- **DOCX and PDF do not block each other.** The completion report's note that "DOCX and PDF share import logic in places" refers to `styledImport.ts`'s use of `@xmldom/xmldom` for DOCX specifically (unrelated to PDF's `pdfjs-dist`-based import) — there is no real shared import mechanism between the two formats that would make refactoring one simplify the other.
- **HTML/Markdown should be scheduled last, if at all**, given its size, risk, and the fact that no other unit's refactor makes it easier — it's an independent, self-contained problem whose main argument for doing it is gate 3 completeness, not any functional need.
