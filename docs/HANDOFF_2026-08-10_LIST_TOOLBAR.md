**A real bug in this session's own implementation, caught by its own test:** the `createList` rewrite initially assigned item IDs out of document order — the deepest/most-nested item could grab an ID meant for an item that appears earlier in the source sequence, because the recursive nested-list build was embedded inside an object-literal `children:` expression that got evaluated before the outer item's own ID was claimed. Fixed by hoisting the ID claim to the top of each loop iteration in `buildListItems`. Worth remembering: this class of bug (implicit evaluation-order dependency inside object literal construction) is easy to introduce again if this function is touched further.

## 2. Two bugs reported this session that could NOT be reproduced

Both got a serious reproduction effort — not a quick dismissal:

**a) "List at the end of the editor, double-Enter doesn't exit, just keeps adding numbered items."** Reproduced three separate ways in real Chromium/Firefox/WebKit via Playwright (seeded multi-item document, toolbar-created + typed content, single- and multi-item lists, numbered and bulleted, including a third Enter afterward to rule out looping back into list mode). All exit correctly on the second Enter. Existing jsdom tests (`packages/core/src/foundation/phase2_5.test.ts`: "exits a depth-zero list from the newly-created empty trailing item", "exits after a trailing list item instead of creating empty items forever") and e2e test (`canonical-authority.spec.ts`: "deletes the empty paragraph after Enter exits a list") all pass.

**b) "Select an existing multi-level nested list entirely, click Bullets or Numbering, and every line shows a stray '1.' alongside the original bullet markers — clearly wrong."** Tried three reproduction shapes (single deep chain; three siblings with one carrying a deep chain; via both API-driven `setSelection` and a *real* Playwright mouse-drag selection), checked both the resulting model structure and the actual rendered `innerHTML`. Every attempt came back completely clean — correct `<ol>`/`<ul>` nesting, `list-style-type` set correctly, no literal "1." text anywhere, no stale `data-srte-list-preset` attributes left over.

**Leading hypothesis for both, given the pattern:** `smartrte-core`/`smartrte-react` are already published on the public npm registry, and there's a large amount of uncommitted, actively-changing work in this tree from outside this session (see §3). A stale build — testing against the published package or an older commit rather than this exact live-source dev server — has already been the confirmed root cause of at least one prior "not working" report in this same bug-hunt lineage (see `PHASE_8B_MIXED_CHECKBOX_PRESET_REOPEN.md`'s checkbox section). **Before spending more time on either of these, get confirmation of what build/environment reproduces them.** If reproducible against this exact workspace's dev server, get either the exact click sequence or an exported document JSON — guessing at the structure has not worked twice now.

## 3. A real, understood, un-fixed gap (found while chasing 2b above)

`unwrapList` (`commands.ts:277-332`) only unwraps items that are **direct children** of the list it resolves to (via `directItemIndexes`, `commands.ts:68-71`). When a selection spans multiple nesting depths at once, the scope resolver correctly produces one unified `list-selection` covering every touched item across all depths — but `unwrapList` silently ignores any of those items that aren't direct children of the resolved (root) list. Practically: select a multi-level nested list fully and click the already-active toggle button, and only the top-level items get unwrapped; deeper items stay nested.

This is a plausible (not confirmed) explanation for bug 2b above, but wasn't proven to be the cause — the reproduction attempts for 2b didn't hit this path cleanly either (see §2).

**Fixing it properly requires a pattern with no precedent anywhere in this command layer:** processing nesting levels deepest-first and recomputing positions against a progressively-updated intermediate document (calling `applyOperations` internally within the command, then continuing to compute more operations against that result) rather than the current approach of computing every operation from one static initial snapshot. Confirmed via grep that no command in `packages/core/src/foundation/{list,block,table}/commands.ts` currently does this. Not started — needs a decision on whether it's worth the complexity before investing in it, and ideally confirmation that it's actually what's causing a reported symptom rather than a theoretical gap.
